# Hangulji 포팅 명세 (SPEC.md)

이 문서는 Kotlin(Android)·Windows 브리지 등 macOS 이외 플랫폼 포트가 구현해야 할 알고리즘을 언어 중립적으로 서술한다. **레퍼런스 구현은 `core-swift/Sources/HanguljiCore`(Swift)이며, 이 문서는 그 동작을 기술한 것이다.** 문서와 코드가 어긋나면 코드가 옳다 — 이 문서를 고친다.

포트가 자신의 구현이 맞는지 확인하는 유일한 방법은 이 문서 + `spec/mapping.tsv` + `spec/fixtures/*.json`이다. 세 산출물이 포트의 요구사항 전체이며, Swift 소스를 읽을 필요는 없다(읽어도 무방하지만 필수는 아니다).

## 0. 매핑 철학 (요약)

한글 1음절 = 가나 철자 1모라로 대응시킨다. 격음(ㅋㅌㅍ+ㅊ·ㅅ)은 청음, 평음(ㄱㄷㅂㅈ)은 탁음으로 대응하며 어두/어중 위치는 구분하지 않는다. 국립국어원 외래어 표기법(비가역적 — 어두/어중 구분, 장음 소실, ず=づ 병합)은 채택하지 않는다: 로마지 입력이 발음(Tokyo)이 아니라 철자(toukyou)를 그대로 타이핑하듯, 이 입력기도 가나 철자에 충실하게 한글을 대응시킨다.

전체 대응표(기본 음절표, 관용 별칭, 확장 가타카나용 음절)는 이 문서에 중복 기술하지 않는다 — **`spec/mapping.tsv`가 유일한 매핑 진실 원천**이다. 철학과 근거의 전체 서술은 `docs/superpowers/specs/2026-07-31-hangulji-ime-design.md` §4를 참고한다.

## 1. 키맵 — 2벌식 라틴 → 자모

하드웨어 자판(QWERTY 물리 배열)의 각 키가 소문자로 눌렸을 때와 Shift(대문자)로 눌렸을 때 어떤 자모가 되는지를 정의하는 표다. 표에 없는 조합(예: Shift+A)은 §1.1의 대문자 폴백 규칙을 따른다.

표에 실제로 배정된 항목 수는 소문자 26개 + 대문자(Shift) 7개(Q W E R T O P) = **33항목**이다. 이것이 키맵 표의 전부다(19개 자음 전부 + 21개 모음 중 14개가 직접 배정되고, 나머지 7개 모음 ㅘㅙㅚㅝㅞㅟㅢ는 키 배정이 아니라 §2.4의 복합모음 결합 규칙으로만 만들어진다).

- 표에 없는 키(숫자, 나머지 알파벳, 기호 등)는 자모가 아니다.
- `-` 키는 자모가 아니라 별도 기호(장음 ー)로 처리한다 — §4 참고.

### 1.1 대문자 폴백 규칙

별도로 배정되지 않은 대문자(Shift로 입력된 알파벳)는 **같은 위치의 소문자와 동일하게 취급**한다. 예: Shift+A(대문자 `A`)는 별도 배정이 없으므로 소문자 `a`와 동일하게 ㅁ이 된다. 판정 순서:

1. 입력 문자가 표에 정확히 일치하는 항목이 있으면 그 항목을 쓴다(소문자든, Q/W/E/R/T/O/P 같은 명시적 대문자든).
2. 표에 없고 입력 문자가 대문자이면, 그 문자를 소문자로 바꿔 다시 표를 찾는다.
3. 그래도 없으면 자모가 아니다(자판 소비 안 함).

## 2. 음절 조합 automaton (JamoComposer)

### 2.1 상태

자모 스트림(키 입력이 자모로 변환된 순서열)을 받아, 아래 세 필드로 이루어진 "현재 음절" 누적기 하나를 유지하며 왼쪽에서 오른쪽으로 처리한다.

- **초성**(선택, 자음)
- **중성**(선택, 모음)
- **종성**(선택, 자음 — ㄸㅃㅉ는 종성이 될 수 없다. §2.5)

구현은 자모 스트림 전체를 매 순간 처음부터 재계산한다(스트림이 짧으므로 증분 갱신보다 단순함이 우선). 포트가 증분 방식으로 구현해도 무방하나, 아래 규칙을 순서대로 적용했을 때와 **동일한 완성 음절 목록**을 내야 한다.

처리 결과는 "완성된 음절" 목록이며, 각 음절은 §2.7의 규칙으로 화면 표시용 문자열(완성형 한글 또는 낱자)로 렌더링된다. 스트림을 다 처리한 뒤 누적기에 남아 있는(비어 있지 않은) 음절도 목록 끝에 포함한다(flush).

### 2.2 전이 규칙 — 자음 도착

현재 누적기 상태에 따라 분기한다:

1. **현재 음절에 중성이 아직 없다면:**
   - 초성도 아직 없다면 → 이 자음을 초성으로 채운다.
   - 초성이 이미 있다면(=자음이 중성 없이 연달아 들어온 경우, 예: ㄱㄴ) → 현재 음절을 완성 목록으로 flush하고, 이 자음을 새 음절의 초성으로 시작한다.
2. **현재 음절에 중성이 있다면:**
   - 초성이 있고, 종성이 아직 없고, 이 자음이 종성이 될 수 있는 자음(§2.5)이면 → 종성으로 채운다.
   - 그 외의 경우(초성이 없거나 / 종성이 이미 있거나 / 이 자음이 종성 불가) → 현재 음절을 flush하고, 이 자음을 새 음절의 초성으로 시작한다.

### 2.3 전이 규칙 — 모음 도착 (받침 재해석 포함)

1. **현재 음절에 종성이 이미 있다면 → 받침 재해석**: 그 종성을 현재 음절에서 제거한 뒤(종성 없는 상태로) 현재 음절을 완성 목록으로 flush하고, 방금 제거한 종성 자음을 **새 음절의 초성**으로, 이번에 도착한 모음을 그 새 음절의 중성으로 삼아 새 음절을 시작한다. (예: ㄱㅏㄴ 다음에 ㅣ가 오면 "간"이 아니라 "가" + "니"가 된다 — 종성 ㄴ이 다음 음절 초성으로 재배정됨.)
2. **종성이 없고, 중성도 아직 없다면** → 이 모음을 중성으로 채운다.
3. **종성이 없고, 중성이 이미 있고**, 현재 중성과 이번 모음의 조합이 §2.4의 복합모음 결합표에 있다면 → 중성을 그 결합 결과로 교체한다(복합모음화).
4. **그 외의 경우**(중성이 있고 결합표에도 없는 모음 — 예: 모음이 중복 입력됨) → 현재 음절을 flush하고, 이번 모음을 초성 없는 새 음절의 중성으로 시작한다.

### 2.4 복합모음 결합표

일본어 표기에 필요한 조합과 표준 한글 복합모음 일부만 지원한다. 아래 표에 없는 모음 쌍은 결합되지 않고 규칙 2.3-4(flush 후 새 음절)를 따른다.

| 앞 중성 | + 도착 모음 | = 결합 결과 |
|---|---|---|
| ㅗ | ㅏ | ㅘ |
| ㅗ | ㅐ | ㅙ |
| ㅗ | ㅣ | ㅚ |
| ㅜ | ㅓ | ㅝ |
| ㅜ | ㅔ | ㅞ |
| ㅜ | ㅣ | ㅟ |
| ㅡ | ㅣ | ㅢ |

### 2.5 종성 가능 자음 (canBeFinal)

19개 자음 중 **ㄸ, ㅃ, ㅉ는 종성이 될 수 없다**(한글 정서법상 원래 종성이 존재하지 않는 자음). 나머지 16개 자음은 모두 종성이 될 수 있다. 이 판정은 §2.2 규칙 2(자음이 종성으로 채워질 수 있는지 여부)와 §2.7의 유니코드 조합 공식(종성 인덱스 유무) 양쪽에서 쓰인다.

### 2.6 백스페이스

백스페이스 1회는 자모 스트림에서 **자모 1개**를 제거한다(음절이나 문자 단위가 아니라 자모 단위). 제거 후 전체 스트림을 §2.1~2.5 규칙으로 처음부터 다시 조합한다. 스트림이 비어 있으면 백스페이스는 아무 효과가 없다.

이 자모 단위 삭제는 `HanguljiComposer` 레벨(§5)에서는 "자모 또는 `-` 토큰 1개 제거"로 확장된다 — 자모 스트림과 `-` 기호가 하나의 토큰 스트림으로 섞여 있기 때문이다.

### 2.7 한글 렌더링 — 유니코드 완성형 조합 공식

완성된(또는 조합 중인) 음절 하나를 화면에 표시할 문자열로 바꾸는 규칙이다.

- **초성과 중성이 모두 있으면** 유니코드 한글 완성형 코드포인트를 계산한다:

  ```
  코드포인트 = 0xAC00 + (초성_인덱스 × 21 + 중성_인덱스) × 28 + 종성_인덱스
  ```

  종성이 없으면 종성_인덱스 = 0을 쓴다. 이 코드포인트를 그대로 유니코드 스칼라 값으로 갖는 1글자 문자열이 표시 문자열이다.
- **초성만 있고 중성이 없으면** 그 자음의 낱자 문자(예: `ㅋ`) 자체가 표시 문자열이다.
- **중성만 있고 초성이 없으면** 그 모음의 낱자 문자(예: `ㅏ`) 자체가 표시 문자열이다.
- **아무것도 없으면** 빈 문자열이다.

## 3. 가나 매핑 규칙 (KanaMapper)

완성된 음절(§2)을 가나 문자열로 바꾸는 규칙이다. 한 음절은 **몸통**(초성×중성)과 **종성**(선택) 두 부분으로 나뉘어 각각 독립적으로 조회된다.

1. 음절에 **초성 또는 중성 중 하나라도 없으면**(즉 낱자 하나짜리 미완성 음절 — 초성만 있거나 중성만 있는 경우 모두 포함) 매핑 불가로 처리한다 → 표시 문자열은 §2.7의 한글 렌더링 그대로, `매핑됨 = false`.
2. 음절에 초성·중성이 모두 있으면, `spec/mapping.tsv`의 **body**(kind=body) 항목에서 (초성, 중성) 조합을 조회한다.
   - 조회에 실패하면(표에 없는 초성×중성 조합) → 매핑 불가: 표시 문자열은 그 음절의 §2.7 한글 렌더링, `매핑됨 = false`.
   - 조회에 성공하면 그 가나 문자열을 "몸통 가나"로 얻는다.
3. 음절에 **종성이 없으면** → 매핑 결과는 몸통 가나 그대로, `매핑됨 = true`.
4. 음절에 **종성이 있으면**, `spec/mapping.tsv`의 **final**(kind=final) 항목에서 그 종성 자음을 조회한다.
   - 조회에 실패하면(그 자음이 종성 매핑표에 없음 — 실제로는 ㄱㄴㄷㅁㅂㅅㅇ 7개만 존재) → 매핑 불가: 표시 문자열은 음절 전체의 §2.7 한글 렌더링(몸통만이 아니라 종성까지 포함한 완성형), `매핑됨 = false`.
   - 조회에 성공하면 매핑 결과는 "몸통 가나 + 종성 가나"를 이어붙인 문자열, `매핑됨 = true`.

핵심 원칙: **몸통 또는 종성 둘 중 하나라도 표에 없으면 그 음절 전체가 매핑 불가**로 취급되며, 부분적으로 가나로 바꾸지 않고 해당 음절 전체를 한글 그대로 표시에 남긴다. `매핑됨(fullyMapped/isMapped)` 플래그는 스트림 전체에 대해서는 "포함된 모든 음절이 매핑 성공했는가"로 집계된다(§5 참고) — 하나라도 실패하면 전체가 `false`.

`spec/mapping.tsv`의 형식: 탭 구분 4열 `kind(body|final)\t초성\t중성(final 행은 공란)\tkana`. 이 파일이 body/final 테이블의 유일한 진실 원천이며, 각 언어 구현의 테이블 상수는 이 파일에서 생성기로 만든다(§7).

## 4. 기호 처리 (`-` / `.` / `,`)

- **`-`(하이픈)**: 장음 기호 ー에 대응한다. 자모가 아니지만 **조합 스트림에 포함되는 토큰**이다(§5의 `HanguljiComposer` 토큰 스트림 참고) — 즉 자모 스트림과 별개로 취급되지 않고, 같은 스트림 안에서 자모 연속 구간을 끊는 구분자 역할을 하며 화면에는 그 자리에 그대로 `ー`로 표시되고 항상 매핑 성공(`매핑됨 = true`) 취급된다. 백스페이스로 자모와 동일하게 1개 단위로 지워진다.
- **`.`(마침표) → `。`**, **`,`(쉼표) → `、`**: 이 두 기호는 조합 스트림에 포함되지 않는다 — 자모도 아니고 `-`도 아니므로 automaton/토큰 스트림 레벨(§2, §5)에서는 그냥 소비되지 않는 입력이다. 이 매핑은 **셸(입력기 컨트롤러) 레벨**에서 처리한다: 조합 중(또는 후보 선택 중)에 `.`나 `,`가 들어오면, 먼저 현재 조합(또는 선택 중인 후보)을 확정 커밋한 뒤, 그 확정된 텍스트 뒤에 이어서 `。` 또는 `、`를 별도로(조합 스트림에 넣지 않고) 삽입한다. 조합 중이 아닐 때도 동일한 동작(커밋할 것이 없으면 커밋은 아무 효과 없이 넘어가고 기호만 삽입)이다.

포트는 `-`는 코어(automaton/토큰 스트림) 레벨에서, `.`/`,`는 셸(플랫폼별 입력 컨트롤러) 레벨에서 구현해야 하며, 코어의 fixture 골든에는 `.`/`,` 케이스가 등장하지 않는다(코어가 소비하지 않는 입력이므로).

## 5. 조합 파사드와 토큰 스트림 (HanguljiComposer)

셸이 실제로 사용하는 것은 §2의 순수 자모 automaton이 아니라, 자모와 `-`(장음) 기호를 함께 다루는 상위 파사드다. 내부적으로는 **토큰 스트림**을 유지하며, 토큰은 다음 두 종류뿐이다:

- **자모 토큰**: §1 키맵으로 변환된 자음/모음 하나.
- **장음 토큰**: `-` 키 입력 하나(ー에 대응, §4).

동작:

- **입력 소비**: 들어온 문자가 키맵(§1)에 있으면 자모 토큰으로 스트림에 추가하고 소비됨(true)을 알린다. 문자가 `-`이면 장음 토큰으로 추가하고 소비됨을 알린다. 그 외 문자는 스트림에 추가하지 않고 소비 안 됨(false)을 알린다(셸이 §4 후반부 규칙이나 시스템 기본 동작으로 처리).
- **백스페이스**: 토큰 스트림에서 **토큰 1개**(자모든 장음이든 종류 무관하게)를 제거한다. §2.6과 일관되게, 자모 스트림 안에서의 삭제는 자모 automaton 재계산과 맞물린다.
- **표시/독법 계산**: 토큰 스트림을 장음 토큰을 경계로 "자모 연속 구간"들로 나눈다. 각 자모 연속 구간은 독립적으로 §2 automaton에 통과시켜 완성 음절 목록을 얻고, 그 목록을 §3 규칙으로 가나(또는 매핑 실패 시 한글)로 바꾼다. 장음 토큰은 그 위치에 그대로 `ー`(항상 매핑 성공)로 끼워 넣는다. 이렇게 얻은 "요소들"(가나 조각/한글 조각/ー)을 스트림 순서대로 이어 붙인 것이 **markedText**(조합 중 표시 문자열)다.
- **reading**(한자 변환 가능 여부 판정용 독법): 요소가 하나도 없으면(빈 스트림) 없음(nil)이다. 요소가 하나 이상 있고 **그 요소 전부가 매핑 성공**이면 markedText와 동일한 문자열을 reading으로 낸다. 요소 중 하나라도 매핑 실패(한글 그대로 남은 조각)가 있으면 reading은 없음(nil)이다 — 즉 완전히 가나로 바뀌었을 때만 한자 변환을 시도할 수 있다는 신호다.

## 6. 픽스처 포맷과 포트의 러너 의무

`spec/fixtures/`에는 언어 중립 골든 테스트 케이스가 JSON으로 들어 있다. **모든 포트(Kotlin/Android, Windows 브리지 포함)는 이 두 파일을 읽어 검증하는 자체 언어의 테스트(conformance 러너)를 가져야 하며, 그 테스트는 각 포트의 CI에 포함되어야 한다.** 두 파일 다 통과해야 그 포트는 "코어 동일성(conformance)"을 만족한 것으로 간주한다.

### 6.1 `kana.json` — §5 HanguljiComposer 레벨 골든

배열의 각 원소는 다음 필드를 갖는 객체다:

| 필드 | 타입 | 의미 |
|---|---|---|
| `name` | string | 케이스 식별자(사람이 읽는 이름, 유일할 필요는 없으나 유일하게 관리됨) |
| `keys` | string | §1 키맵 문자(자모가 되는 문자) + `-` 로만 이루어진 입력 시퀀스. `.`/`,` 같은 셸 레벨 기호는 등장하지 않는다(§4). |
| `kana` | string | `keys`를 한 글자씩 순서대로 HanguljiComposer에 입력했을 때 기대되는 `markedText` 결과(가나와, 매핑 실패 시 한글이 섞일 수 있음). |
| `fullyMapped` | boolean | 같은 입력 뒤 기대되는 `reading != null`(=완전 매핑) 여부. |

**러너 의무**: 각 케이스에 대해 새 HanguljiComposer(또는 동등한 상태)를 만들고, `keys`의 각 문자를 순서대로 삽입한 뒤, 결과 markedText가 `kana`와 문자 그대로 일치하는지, 그리고 (reading이 널이 아님)이 `fullyMapped`와 일치하는지 검증한다. 현재 최소 38개의 완전 매핑 케이스 + 1개의 매핑 불가 케이스(`unmappable`)가 있으나, 러너는 개수를 하드코딩하지 말고 파일에 있는 만큼 전부 순회해야 한다.

### 6.2 `composition.json` — §2 JamoComposer 레벨 골든

배열의 각 원소는 다음 필드를 갖는 객체다:

| 필드 | 타입 | 의미 |
|---|---|---|
| `name` | string | 케이스 식별자 |
| `keys` | string | §1 키맵 문자로만 이루어진 입력 시퀀스(자모만, `-` 미포함 — 이 픽스처는 순수 automaton 레벨이므로 장음 토큰과 무관). |
| `syllables` | string[] | `keys`를 자모로 변환해 순서대로 §2 automaton에 넣었을 때 기대되는 완성 음절 목록. 각 원소는 그 음절의 §2.7 한글 렌더링 문자열(완성형 1글자 또는 미완성 낱자 1글자). |

**러너 의무**: 각 케이스에 대해 새 JamoComposer(또는 동등한 상태)를 만들고, `keys`의 각 문자를 자모로 변환해(변환 실패 시 테스트 실패) 순서대로 추가한 뒤, 결과 음절 목록을 §2.7 규칙으로 렌더링한 문자열 배열이 `syllables`와 순서·개수·내용 모두 일치하는지 검증한다. 현재 최소 8개 케이스가 있으며, 여기에도 개수를 하드코딩하지 않는다(받침 재해석, 복합모음, 종성 불가 자음, 낱자 미완성 등 §2의 대표 규칙들을 각각 커버하는 케이스들이다).

## 7. 변경 절차

매핑이나 automaton 규칙을 바꿀 때는 아래 순서를 지킨다. **Swift 구현이 레퍼런스이므로 반드시 spec → Swift → 그 외 포트 순서로 전파한다.**

1. **spec 수정**: 매핑 대응을 바꾸거나 추가한다면 `spec/mapping.tsv`(탭 구분 4열: `kind\t초성\t중성\tkana`, final 행은 중성 열을 비워 둠)를 고친다. automaton 규칙 자체를 바꾼다면(예: 복합모음 결합표 추가) 이 SPEC.md의 해당 절도 함께 고친다. 새 골든 인터랙션 케이스가 필요하면 `spec/fixtures/kana.json` / `composition.json`에 케이스를 추가한다(또는 아래 3단계의 fixture-export로 자동 기록).
2. **Swift 생성기 재실행**: 저장소 루트에서 `swift spec/generators/gen-swift.swift`를 실행해 `core-swift/Sources/HanguljiCore/KanaTable.generated.swift`를 mapping.tsv로부터 다시 생성한다. 이 파일은 수기 수정 금지이며 항상 생성기 산출물이어야 한다.
3. **fixture-export 재실행**: `core-swift` 디렉터리에서 `swift run fixture-export`를 실행한다. 이 도구는 사람이 정한 골든 케이스(한글 문자열 기준)를 Swift 레퍼런스 구현으로 직접 검증(불일치 시 즉시 실패)한 뒤 그 결과를 `spec/fixtures/kana.json` / `composition.json`으로 (재)기록한다. 즉 픽스처 파일은 항상 "검증된 상태"로만 갱신된다.
4. **Swift 테스트 실행**: `core-swift`에서 `swift test`를 실행해 전체 스위트(단위 테스트 + `FixtureTests.swift` conformance 러너 포함)가 통과하는지 확인한다. 이 단계가 게이트다 — Swift가 초록이 아니면 다음 단계로 넘어가지 않는다.
5. **각 포트 갱신**: 모든 포트는 `spec/mapping.tsv`로부터 테이블 상수를 생성기로 재생성해야 한다 — 해당 언어용 생성기가 있다면 그것을 실행하고, 없다면 이번 기회에 작성한다. 수기 수정(수동으로 동등하게 갱신)은 금지한다(설계 §4 참고). Kotlin(Android) 쪽 테이블 상수, Windows 브리지의 대응 테이블/로직 모두 동일하게 생성기 산출물이어야 한다. 이어서 각 포트 자체의 §6 conformance 러너(같은 `spec/fixtures/*.json`을 읽는 자기 언어 테스트)를 돌려 통과를 확인한다.
6. 모든 포트의 conformance 러너가 갱신된 픽스처로 통과해야 변경이 완료된 것으로 간주한다(CI 게이트).
